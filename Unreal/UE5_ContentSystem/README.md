# UE5 컨텐츠 시스템

반복해서 추가되는 아웃게임 컨텐츠를 한 틀로 찍어내는 시스템이다. 도메인마다 데이터를 소유하는 모델을 두고,
서버와의 요청/응답/노티, 캐시, UI 통지를 프레임워크가 공통으로 맡는다. 컨텐츠를 새로 붙일 때
프레임워크 코드는 건드리지 않는 걸 목표로 했다.

클라이언트 코드만 담았다. 서버가 요청을 받아 응답을 만드는 몫은 이 모듈에 두지 않았고,
실서버가 붙어도 그대로 남을 클라 쪽 계약과 흐름만 있다.

## 구조

```
[Framework]  PAContentModelManagerBase   모델을 스캔해 등록하고 수명주기(로그인/리셋)를 돌린다
             PAContentModelBase          도메인 데이터를 소유하고 변경을 통지한다. 캐시·패킷 바인딩
             PAContentNetworkBase        요청/응답/노티. 메시지 id당 핸들러 하나
             PAContentMessage            순수 C++ 자가 직렬화 메시지 + (요청-응답)
             PAContentEventDispatcher    태그 기반 이벤트 채널 (도메인 간 종속성 제거)
             PAContentTypes              캐시 정책 / 요청 결과 enum
[Game]       PAGameContentModelManager   게임 매니저 — 게임 네트워크를 등록
             PAGameContentNetwork        프로토콜 id <-> 메시지 id, 패킷 <-> 메시지 변환
[Domain]     1_Mail_SingleModel          단일 모델 컨텐츠 예시
             2_Collection_MultiModel     부모-자식 다중 모델 컨텐츠 예시
```

객체 관계는 이렇게 놓인다. 매니저가 네트워크와 모델들을 소유하고, 컬렉션은 루트-자식 계층을 가진다.

```
PAGameContentModelManager
 ├── PAGameContentNetwork
 ├── MailContentModel                 (단일 모델)
 └── CollectionContentModel           (루트 — 자식 진행 집계)
        ├── CollectionAppearanceModel
        └── CollectionTitleModel
```

프레임워크는 특정 컨텐츠를 모른다. 도메인이 자기 모델·메시지·이벤트를 한 폴더에서 소유하고,
매니저가 시작할 때 모델을 스캔해 자동으로 등록한다. 그래서 컨텐츠를 추가해도 프레임워크를 수정할 필요가 없다.

## 요청 흐름

UI는 모델을 구독해 두고 캐시를 먼저 그린다. 갱신은 뒤에서 이 순서로 채운다.

```
 1. UI       RefreshCacheIfNeeded() 호출
 2. Model    캐시가 낡았으면 요청 생성
 3. Network  직렬화 → 서버로 전송
 4. Network  서버 응답을 수신 버퍼에 추가
 ───────────  프레임 경계 (다음 월드 틱 시작)  ───────────
 5. Network  버퍼의 패킷을 꺼내 메시지 id로 핸들러를 찾고,
             바이트를 메시지로 역직렬화
 6. Model    핸들러가 캐시 갱신 → OnDataChanged
 7. UI       알림 받고 다시 그린다
```

수신은 도착 즉시(4)가 아니라 프레임 시작(5~6)에 몰아 처리한다. 그 프레임의 게임플레이·UI가 데이터를
읽기 전에 먼저 반영하고, 여러 응답을 도착 순서대로 한 번에 적용하기 위해서다.

## 설계에서 신경 쓴 부분

### 모델 — 데이터를 한 곳에서 소유한다

각 도메인 데이터는 모델 하나가 단독으로 들고 있고, 바뀌면 `OnDataChanged`로 알린다. UI든 게임플레이든
구독해 두고 알림을 받으면 모델에서 다시 읽는다. 데이터의 주인이 하나라, "누가 최신인가"를 따질 일이 없다.
모델은 UI 전용 데이터가 아니라 게임플레이가 필요로 하는 데이터도 같은 방식으로 담는다.

### 컨텐츠 일반화 — 프레임워크는 도메인을 모른다

컨텐츠를 붙이는 비용을 낮추는 게 이 시스템의 핵심이다. 새 컨텐츠는 모델·메시지·이벤트 세 벌만 자기 폴더에
쓰면 되고, 등록은 매니저가 시작할 때 파생 모델을 스캔해 자동 등록 되도록 한다.

컬렉션은 부모-자식 계층까지 쓰도록 설계 했다. 부모 모델이 자식들의 `OnDataChanged`를 구독해, 자식 컬렉션이 바뀌면
진행 수치를 다시 집계하고 요약 이벤트를 낸다. 계층·집계가 도메인 안에서만 돌고 프레임워크는 그대로다.

| 계층 | 메일(1차) | 컬렉션 추가 시 변경 |
|---|---|---|
| Framework | 6파일 | **0줄** |
| Game (구현체) | — | 프로토콜 테이블 매핑 몇 줄 |
| Domain | 메일 도메인 | 신규 9파일 (메시지 1 · 이벤트 2 · 모델 3벌) |

구현 예시는 `SampleContents/`의 메일(단일 모델)·컬렉션(부모-자식 다중 모델)에 있다.

### 캐시 — 언제 다시 받을지를 정책으로 나눈다

목록을 매번 새로 받으면 낭비고, 한 번 받고 안 갱신하면 낡는다. 그래서 재취득 시점을 정책으로 분리했다.
세션 내 1회만 받는 것(`CacheUntilInvalidated`), 수명이 지나면 다시 받는 것(`CacheWithLifetime`),
매번 받는 것(`NoCache`) 셋이다. 데이터가 필요할 때는 조건을 따지지 말고 `RefreshCacheIfNeeded`를 부르면,
정책과 대기 상태를 보고 실제 요청 여부를 베이스가 판단한다. 응답을 기다리는 중이면 중복 요청을 막도록 하였다.

바뀐 데이터를 받는 방식은 컨텐츠마다 다르다. 컬렉션은 한 번 받아 두고, 이후 획득 노티가 오면 캐시의 그 항목에
해당하는 캐시 데이터만 수정한다. 메일은 새 메일 노티가 개수만 실어 와서 목록을 제자리에서 고칠 수 없으니, 캐시를 무효화하고
다음에 열 때 다시 받는다. 노티에 실린 정보가 무엇이냐에 따라 선택적으로 캐시를 관리한다.

### 네트워크 — 메시지가 자기를 직렬화한다

메시지는 순수 C++ 구조체이고, 직렬화 함수 하나를 저장·로드 겸용으로 쓴다(`Ar << Field`). 읽기용·쓰기용을
따로 두지 않아서 고칠 곳이 한 군데다. 대신 필드를 더하거나 바꿀 때 이 직렬화 함수도 같이 고쳐야 한다.

요청 타입이 자기 응답 타입을 품고 있어서, 전송 함수가 컴파일 시점에 짝을 강제한다.
엉뚱한 응답 타입으로 받는 실수가 타입 단계에서 걸린다. 수신 쪽은 메시지 id마다 핸들러가 하나뿐이고,
같은 id에 둘을 등록하면 에러로 잡는다 — "이 패킷은 이 도메인 것"이라는 규칙을 런타임이 강제한다.

### 수신 — 프레임 시작에 몰아서 처리한다

응답·노티는 도착하는 대로 처리하지 않고 버퍼에 쌓아 두었다가, 게임 스레드에서 다음 월드 틱이 시작하기
직전에 도착 순서대로 한 번에 처리한다. 그 프레임의 게임플레이·UI가 데이터를 읽기 전에 먼저 반영하려는
것이다("패킷 먼저"). 아무 때나(경우에 따라 다른 스레드에서) 도착하는 수신을 게임 스레드의 정해진 한 지점으로
모으는 역할도 한다. 처리 도중 새로 도착한 메시지는 다음 처리로 넘긴다.

### 이벤트 — 종속성을 줄여 복잡도를 낮춘다

안 읽은 메일 수, 수집 진행도처럼 여러 시스템이 보는 값을 직접 델리게이트로 이으면 발신자가 수신자를 다 알아야
해서 종속성이 폭발한다. 그래서 태그 채널로 뿌린다. 보내는 쪽은 누가 듣는지 모르고, 듣는 쪽은 어느 도메인이
보냈는지 모른다. 채널은 무상태라, 늦게 구독한 쪽은 이벤트를 기다리지 않고 모델에서 현재 값을 바로 읽어 그린 뒤
다음 알림부터 갱신한다. 채널의 페이로드 타입은 첫 등록 때 고정하고, 다른 타입으로 보내면 에러로 잡아 채널이
섞이는 걸 막는다.
